## 18db662 - Access-Code Email Wording And Layout

**Date:** 2026-10-17 00:08 Europe/Moscow
**Author:** kv@agg.one
**Context:** Access-code emails landed in Gmail's spam folder and, once that was fixed, looked unlike the one-time-code emails users are used to. Gmail also auto-linked anything domain-shaped in the body, so `secreto.info` kept rendering as a link even after the anchors were removed. Several rounds of wording were tried against a real inbox (PRs #11 through #21).
**Changed:** The code email now has the subject `Secreto Verification Code`, a "Your verification code" heading, a one-line intro and a single styled code block. The body names the service as `SECRETO` and contains no domain, no recipient address and no link other than unsubscribe; the sending identity (`EMAIL_FROM`) carries the domain. The expiry is spelled out in words so the code is the only number in the message. The no-access email follows the same shape. Intermediate experiments — code in the subject, a `Code:` line under the block, a numbered copy-paste layout — were tried and reverted.
**Files:** `packages/app-server/src/modules/notes/email-gate/email.services.ts`.
**Reasoning:** Mail clients detect one-time codes heuristically; there is no markup to opt into Gmail's "copy code" chip, and schema.org email markup covers orders and events, not OTPs. What is controllable is the shape of the message: recognisable wording, the code as the only number, and nothing that looks like a link to a young sending domain.
**Verification:** Each iteration was rendered locally with a stubbed Resend call (subject, HTML, plain-text part, link count, numbers in the body), deployed, and checked by sending a real code to a Gmail account. Final version arrives in the inbox. The code chip did not appear; it is generated by Gmail's own models and cannot be requested.
**Risks:** Deliverability still depends on the reputation of `secreto.info`, which has been sending for about three weeks. Wording changes are cheap to revert — the commit before the final layout is `1de0fbd`.
**Next steps:** Watch Google Postmaster Tools once volume is high enough to produce data.

## 1de7e00 - CLI 0.3.0: Configurable Instance And Readable Network Errors

**Date:** 2026-09-22 22:51 Europe/Moscow
**Author:** kv@agg.one
**Context:** A fresh machine reported `fetch failed` from `secreto-cli` with no further detail. The published package turned out to be fine — that string is what Node prints for any transport problem — but the CLI passed it through unchanged, and the instance URL was hardcoded, so self-hosted deployments could not use it at all.
**Changed:** Added `--instance` and `SECRETO_INSTANCE_URL`; `secreto get` derives the instance from the note URL. Network failures are now reported with the host and cause (DNS, refused, timeout, TLS), plus a hint when `HTTP_PROXY`/`HTTPS_PROXY` is set, since Node ignores those unless run with `NODE_USE_ENV_PROXY=1`. Added `--stdin`, which the docs already described but the CLI did not implement, and `engines: node >=18`. Corrected the documented TTL values (`1h`/`1d`/`1w`/`1m`) and the note URL format. Published to npm as 0.3.0 on 2026-10-17.
**Files:** `packages/cli/src/index.ts`, `packages/cli/README.md`, `packages/cli/package.json`, `packages/docs/src/integrations/cli.md`.
**Reasoning:** The opaque error cost an hour of looking in the wrong place. Making the CLI say which host it could not reach, and letting it point at another instance, turns the same report into a one-line answer.
**Verification:** Lint and typecheck made clean for the package. Against production: send/get roundtrip, password-protected roundtrip, `--file`, `--stdin`, piped input without the flag, plain argument. Error paths exercised with an unresolvable host, a refused connection, an unroutable address and an invalid `--instance`. After publishing, verified a clean global install of 0.3.0.
**Risks:** Publishing is manual; there is no CI pipeline for the CLI. npm clients may serve a cached 0.2.0 until `--prefer-online`.
**Next steps:** Automate the npm publish if the CLI starts changing often.

## 4fd0dab - Admin Area And PostgreSQL

**Date:** 2026-09-21 23:17 Europe/Moscow
**Author:** kv@agg.one
**Context:** The opt-out list lived in Supabase, whose project had disappeared — its host no longer resolved — so opt-outs were silently not recorded. There was also no way to see how many notes were being created.
**Changed:** Added optional PostgreSQL storage behind `DATABASE_URL`, with versioned migrations applied on first use. Moved the suppression list off Supabase; Supabase configuration is gone. Note creation now writes a `note_events` row in the background with timestamp, lifetime, burn-after-reading flag and number of email recipients — no note IDs, payloads or addresses. Added `/admin`: sign-in against `ADMIN_USERS` (`email:bcryptHash`) with an httpOnly `SameSite=Strict` session cookie and login rate limiting, KPI cards, a 30-day notes-per-day chart, and a searchable, paginated opt-out list with removal.
**Files:** `packages/app-server/src/modules/db/`, `packages/app-server/src/modules/admin/`, `packages/app-server/src/modules/notes/email-gate/suppression.repository.ts`, `packages/app-client/src/modules/admin/`, `packages/docs/src/self-hosting/configuration.md`.
**Reasoning:** A database next to the app removes an external point of failure that had already failed. Everything degrades safely: without a database notes and emails keep working, opt-outs are simply not stored and statistics are unavailable.
**Verification:** New e2e tests for the admin API, with database scenarios gated on `TEST_DATABASE_URL` and run against PostgreSQL 17. The admin page was exercised in a browser — sign-in, stats, chart, search, removal, mobile layout — and note creation was confirmed to work with the database stopped.
**Risks:** The suppression list started empty; opt-outs recorded in Supabase before it vanished are not recoverable. Admin sessions last 12 hours and are revoked by removing the account from `ADMIN_USERS`.
**Next steps:** None outstanding; backups of the database are configured on the server (monthly, upload-only, to `gs://agg-backups-cold`).

## 2230af3 - Transactional Email Content

**Date:** 2026-09-21 21:50 Europe/Moscow
**Author:** kv@agg.one
**Context:** Access-gate emails were bare HTML fragments with no text alternative and no reply address, which reads as low quality to spam filters.
**Changed:** Emails are now complete HTML documents with a shared layout, preheader and footer that states why the recipient got the message and who operates the service. Added an explicit plain-text part and a `Reply-To` header, configurable via `EMAIL_REPLY_TO` (`none` omits it).
**Files:** `packages/app-server/src/modules/notes/email-gate/email.services.ts`, `packages/app-server/src/modules/notes/email-gate/email-gate.env.ts`, `packages/docs/src/self-hosting/configuration.md`.
**Reasoning:** Cheap, standard signals: a document rather than a fragment, both MIME parts, and a way to reply.
**Verification:** Both emails rendered locally with a stubbed Resend call; headers, HTML and text part checked.
**Risks:** None known.
**Next steps:** None.

## 2bb680e - Email Gate: Read Config From The Request Context

**Date:** 2026-09-21 19:21 Europe/Moscow
**Author:** kv@agg.one
**Context:** Access codes were never delivered: every send failed and the API still answered `{ sent: true }`, because the failure was swallowed by a fire-and-forget `.catch(console.error)`. The server logs showed `Resend API error 403: This API key is not authorized to send emails from secreto.info` — the key predated the move to that sender domain. The same investigation found the email gate reading its configuration from `process.env`, which is empty on Cloudflare Workers where variables live on `c.env`.
**Changed:** Email-gate configuration is resolved from `c.env` with a `process.env` fallback for Node. Background sends are registered with `executionCtx.waitUntil` where available. Removed the hardcoded fallback used to sign unsubscribe links — anyone could forge an opt-out for any address — and unsubscribe tokens are now rejected when no secret is configured. The unsubscribe page reports an error instead of claiming success when the opt-out cannot be stored.
**Files:** `packages/app-server/src/modules/notes/email-gate/` (env, routes, middleware, services, unsubscribe token), `packages/docs/src/self-hosting/configuration.md`.
**Reasoning:** The outage was a configuration mismatch, but the code made it invisible. Failures now surface in logs with the cause, and the runtime-specific config lookup matches how the rest of the server already reads its settings.
**Verification:** Ad-hoc vitest run covering a Worker-style request with env on `c.env` and a mock execution context, a Node-style request without one, a forged unsubscribe token and an unconfigured suppression store. On the server, a new Resend key authorised for `secreto.info` was installed through the deployment workflow and a real code arrived in the inbox.
**Risks:** Unsubscribe links signed with the old fallback key no longer validate; in practice no such email had ever been delivered.
**Next steps:** None.
